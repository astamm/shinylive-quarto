2.2 From R Markdown to Quarto

Quarto is a multi-language scientific and technical publishing system built by Posit. If you know R Markdown, you already know 80% of Quarto.

Same ideas. Markdown + code chunks + YAML front matter, rendered to many output formats.

Same engine. R code still runs through knitr; only the chunk-option syntax changes ({r, echo=} → #| echo: lines).

Same workflow. Write a .qmd, click Render / quarto render, get HTML, PDF or slides.

2.3 Similarities with R Markdown

Most of what you already know carries straight over. With a few renames:

  • Chunk syntax. Same three backticks and {r}: ```{r} starts a chunk, unchanged.
  • Chunk options. Now written one per line, #| key: value. Or keep the old {r, echo=TRUE} header form.
  • YAML front matter. Same fields; only output: becomes format:.
  • Inline R in prose. `r 2 + 2` still evaluates at render.
  • One source, many formats. HTML, PDF, docx, revealjs and more.

References: execution options · front matter · output formats

2.6 Quarto projects

A folder with a _quarto.yml becomes a project: one file configuring the whole folder. Four built-in types – website, book, manuscript, or default.

_quarto.yml

project:
  type: default        # default | website | book | manuscript
output-dir: _output
execute:
  freeze: true         # cache results, rerun only when inputs change

format:
  html:
    toc: true
    theme: cosmo

quarto preview rebuilds + live-reloads project as you edit; quarto render builds final output; quarto publish deploys it. See the project reference.

3.1 What Shiny is

Shiny is a framework for interactive web applications: you write an app in R, and Shiny serves it as a web page that reacts to the reader’s actions. It is not a purely R idea – later we note the Python flavour – but we go through R throughout today.

UI. The layout: sliders, buttons, tables, plots, text.

Server. The logic: what happens when the user changes an input.

Reactive wiring. What Shiny calls the “reactive graph”: inputs flow to outputs.

3.2 A minimal Shiny app

Every Shiny app has two pieces. The smallest possible app:

app.R

library(shiny)

ui <- fluidPage(
  sliderInput(inputId = "n", label = "Number of points",
              min = 10, max = 200, value = 50),
  textOutput(outputId = "msg")
)

server <- function(input, output, session) {
  output$msg <- renderText({
    paste("You chose", input$n, "points")
  })
}

shinyApp(ui = ui, server = server)

Run it with Run App (or shiny::runApp("app.R")).

3.3 The reactive model, visually

Shiny tracks dependencies so only what changed re-renders.

Note

Reactive flow:

  • input change invalidates expressions that read it, which in turn invalidate outputs that depend on them
  • Shiny recomputes only that minimal set.

Reactive expression: compute a value once + cache it \(\rightarrow\) dependent outputs reuse a single computation.

3.6 A reactive app with a plot

app.R

library(shiny); library(ggplot2); library(dplyr)
ui <- fluidPage(
  titlePanel("Palmer penguins explorer"),
  fileInput("data", "Upload your data (CSV)", accept = ".csv"),
  sliderInput("bins", "Number of bins", 5, 40, 20),
  plotOutput("hist")
)
server <- function(input, output, session) {
  peng <- reactive({ req(input$data); readr::read_csv(input$data$datapath) })
  output$hist <- renderPlot({
    peng() |> ggplot(aes(body_mass_g)) +
      geom_histogram(bins = input$bins, fill = "#2E7D6B")
  })
}
shinyApp(ui, server)

reactive({}) reads the file once, then re-runs only when the upload changes. Run it at material/apps/penguins-app/app.R.

3.7 Reactive details that trip people up

Reactives are lazy and cached: a reactive({}) recomputes only when its inputs change.

  • req() guards: req(input$x) halts until input$x is non-empty, avoiding errors on first render.
  • eventReactive(): for click-driven actions (button → go), when you do not want recomputation on every keystroke.
  • Side-effects live in observers or render*(): a reactive() only computes a value. To do something when an input changes – a showNotification(), refreshed updateSelectInput() choices, a revealed panel – use an observer (observe()) or an output.

4.1 Why host without a server?

Shiny traditionally needs a server program running around the clock, which takes time, expertise and money to keep up.

Shinylive is the alternative: the whole app becomes plain files that any static host can serve, so the browser does the computing.

  • Non-static (server)
  • Static (Shinylive, GitHub Pages, Netlify)
  • A server program computes and streams results; any package, secret keys; costs money and maintenance.
  • The host just serves files; the reader’s browser runs the app. Free and fast; but WASM-only, no secret keys.

4.2 The three tools behind Shinylive

Three tools, one idea: run R in the browser with no server.

WebAssembly. A portable, sandboxed binary format. Sandboxed: it runs isolated from your computer and the page. Binary: it is compiled machine code in a .wasm file, not human-readable source. Browsers run it at near-native speed.

webR. The R interpreter compiled to WebAssembly, so R runs inside the browser.

Web assets library. A bundle of static JS/CSS/files a page downloads and runs; Shinylive itself is one.

4.3 What is WebAssembly?

WebAssembly (WASM) is a low-level bytecode: the machine-readable instructions a browser executes, run inside a secure sandbox. Think of it as a “portable CPU” that every browser already includes.

  • The idea
  • Why it matters here
  • Languages like C, C++, Rust, R are compiled to .wasm files.
  • The browser runs them at near-native speed, isolated from the page.
  • It powers heavy in-browser apps: editors, games, and now statistical computing.
  • R is normally an installed binary. WASM lets the same R run wherever a browser runs: a phone, a colleague’s computer, GitHub Pages.
  • No server is needed to interpret the code; the browser is the runtime.

Sources: webassembly.org · developer’s guide

4.4 What is webR?

webR is the R interpreter recompiled to WebAssembly, so R runs entirely in the browser. The recipe builds R for the browser in one line:

\[\mathrm{webR} = \mathrm{R} + \mathrm{WASM} + \mathrm{Node.js} + \mathrm{Emscripten}\]

WASM. The new “hardware”: the portable binary every browser executes.

Node.js. The build kitchen: the JS toolchain that assembles R for the web.

Emscripten. The compiler bridge: pure R ports easily, but its C/C++ core needs turning into WASM, which is where Emscripten comes in.

4.5 webR in action

  • Your R packages are compiled to WASM too, available from the webR repository: https://repo.r-wasm.org
  • Popular packages (tidyverse, ggplot2, dplyr, readr) work.
  • webR lets a page call R from JavaScript and render results live.
  • Project home: https://docs.r-wasm.org/webr/latest/

Warning

A package must already be compiled to WASM to run in the browser. Only packages listed in the webR repository (https://repo.r-wasm.org) work out of the box.

Note

Sweet spot. webR means “the same R you use at your desk, inside the reader’s tab”. The data never leaves their computer, and the code they see is the code you wrote.

4.6 What is a web assets library?

A web assets library is a set of static files (JavaScript, CSS, worker scripts, WASM binaries) a page downloads and runs. Shinylive is exactly one: it bundles the machinery to run Shiny in the browser via webR, as files you can drop on any static host.

4.7 What the browser downloads

On first open, the browser pulls down a bundle once:

webR / WASM binaries. The R interpreter run in the browser.

Shiny + Shinylive assets. The framework and glue.

Your app’s code & packages. Your UI/server, plus WASM packages.

Warning

This bundle is the main cost of Shinylive: a “cold start” may take a few seconds on first load; later visits are cached by the browser.

4.10 Pinning versions for the browser

shinylive::export figures out the R packages your app calls and bundles their WASM builds. For deployments that keep working, pin the versions:

With renv. renv::init() once writes a renv.lock; renv::snapshot() captures updates to it as you change packages. shinylive::export reads the lockfile and ships those exact WASM builds, the most reproducible path: the browser gets the same versions you tested.

Without renv. It scans your dependencies and uses the latest webR builds. Fragile: a future package update can silently break a deployed app.

4.13 Anatomy of an interactive block

Wrap a complete Shiny app in a {shinylive-r} code block: the rest of the page is static, the block becomes a live self-contained app.

---
title: "Interactive report"
format: html
filters:
  - shinylive
---
```{shinylive-r}
#| standalone: true
#| components: [editor]
library(shiny)
ui <- fluidPage(
  sliderInput("n", "Samples", 10, 500, 100),
  plotOutput("hist")
)
server <- function(input, output, session) {
  output$hist <- renderPlot(hist(rnorm(input$n), col = "#2E7D6B"))
}
shinyApp(ui, server)
```

4.14 A full interactive report pattern

A realistic report mixes prose, static figures, tables, and one or more {shinylive-r} widgets:

  • Report structure
  • Block options
  • Including code files
  • Narrative sections with static text and figures.
  • A {shinylive-r} block for each interactive tool.
  • TOC, captions, cross-references as usual.
  • #| standalone: true, required: the block is a complete app.
  • #| components: [editor]: show/hide the code editor and viewer.
  • #| viewerHeight: 420: panel height in px.
  • #| layout: vertical: stack editor above viewer.
  • A live gallery of every option: https://www.royfrancis.com/quarto-exp/documents/shinylive/

App logic in a separate .R file? Paste it into the block with a Quarto shortcode, rather than source()-ing it: copy-paste plays far better with Shinylive’s in-browser file system.

```{shinylive-r}
#| standalone: true
{{< include app.R >}}
```

4.17 A word on privacy and data

Because everything runs in the reader’s browser, uploaded data stays local, true of a standalone app and of a {shinylive-r} block in a report alike:

  • Files are read into browser memory; they are never transmitted to the static host.
  • Reader A’s uploaded data is invisible to reader B; closing the tab discards it.
  • This makes Shinylive an excellent fit for sensitive or GDPR-relevant data.

Caution

The flip side: your code is public (it is downloaded to run). Never ship API keys, passwords, or proprietary algorithms in a Shinylive app or report.

5.1 Choosing an interactivity engine

There is no single right answer. Match the engine to the job:

Note

Roughly:

  • static (Shinylive/OJS) = free, private by architecture, but browser-bound.
  • Server Shiny = full power, more cost and ops. Most productions mix both.

5.2 Limitations to remember

Be honest about the trade-offs before committing to Shinylive:

  • Load time: first visit downloads webR + packages; expect a multi-second start.
  • Package availability: only WASM-built packages work; no system libs, no raw sockets.
  • Network: no direct databases; HTTP calls are subject to the host’s CORS rules.
  • Data size: ship data to the browser, so keep payloads small (a few MB max).
  • Secrecy: the code your reader can run is code they can read.

5.3 Automating deployment with GitHub Actions

Manual publishing is fine for a first pass. For reproducibility, automate it.

Two idiomatic options:

  • Standalone app → Pages
  • Quarto doc → Pages

A reusable workflow (posit-dev/r-shinylive, deploy-app.yaml) runs on push:

  • installs R + packages (renv), runs shinylive::export(".", "site"),
  • uploads the site/ artifact to GitHub Pages with proper pages / id-token write permissions.
  • quarto publish gh-pages from a workflow; or,
  • quarto add quarto-ext/shinylive
  • quarto render then a Pages deploy action.

5.4 The workflow in skeleton

name: Deploy app
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Export Shinylive site
        run: Rscript -e 'renv::restore(); shinylive::export(".", "site")'
      - uses: actions/upload-pages-artifact@v4
        with: { path: "site" }
  deploy:
    needs: build
    permissions: { pages: write, id-token: write }
    environment: { name: github-pages, url: ${{ steps.deployment.outputs.page_url }} }
    runs-on: ubuntu-latest
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
name: Deploy report
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: quarto-dev/quarto-actions/setup@v2
      - name: Render report
        run: quarto render report.qmd
      - uses: actions/upload-pages-artifact@v4
        with: { path: "_output" }
  deploy:
    needs: build
    permissions: { pages: write, id-token: write }
    environment: { name: github-pages }
    runs-on: ubuntu-latest
    steps:
      - uses: actions/deploy-pages@v4
